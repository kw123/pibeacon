BLE dongles / radios: what each one was MEASURED to do
======================================================

Written from dongleCatalogue.json in the plugin's preferences folder, which is what the menu item
"Qualify the BLE dongles of one / all RPI.." fills in. Values are the best of every run: 149 runs over
15 distinct VID:PID, latest 2026-10-14.

COMPARE A DONGLE ONLY AGAINST THE OTHER RADIOS OF THE SAME PI, IN THE SAME PLACE. How many packets
a radio delivers depends entirely on how many BLE devices are talking around it, so these are a
ranking, not a specification. The scanner role is decided on MAC COVERAGE - the share of all macs
any radio in that pi heard - not on packets per second: a radio 3x slower that still hears 90% of
the macs misses nothing that matters, a fast one that hears half of them misses beacons outright.

runs / pis say HOW MUCH EVIDENCE is behind a row: 35 runs on 4 pis is a verdict, 1 run on 1 pi is a
hint. A "--" is a measured zero, not an unknown.

CHECK THE VID:PID, NOT THE BOX.  TP-Link and ASUS both moved to new usb ids without changing the
product name, and the new id can behave completely differently: 2357:0604 scans BLE4 and BLE5,
37ad:0600 delivers nothing at all under the same name. btusb's quirks table is keyed on VID:PID,
so an id missing from it leaves the chip on its ROM firmware - nothing on the pi can fix that, it
needs a kernel in which the id has been added.

BROADCOM BCM20702 NEEDS ITS .hcd PATCH, and the plugin ships it. Without it the dongle runs on ROM
firmware and drops off the usb bus on every reset - which looks like a radio that accepts every
command and delivers nothing, or one that reappears under a different hci number mid-run. Debian
and Raspberry Pi OS package only the onboard radios' firmware, so master.py installs the 36 kB
file on every pi at start, inert until a matching controller is probed.
